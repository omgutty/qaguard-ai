# Taste

## Product quality
- Wants the application to have its own identity and look like an actual professional product ("product-grade") even in the first static version, so it's presentable the moment it's deployed (e.g., to Vercel). Confidence: 0.9
- Prefers a dark, precise, data-dense "engineering tool" visual language for dashboards (deep charcoal/near-black `#0A0A0F`–`#111116` layered surfaces, one sparing accent color, monospace for IDs/code, a consistent status color grammar, score rings/gauges rather than plain numbers, restrained purposeful motion, and first-class designed empty/loading/error states). Explicitly stated as "Linear × Vercel × a security/observability dashboard" and "not an AI scaffold." Confidence: 0.9
- Wants the UI to support light mode as well as dark mode via a global theme toggle — dark-only is not acceptable ("as of now it is showing dark mode ui, but i want light mode as well"). Confidence: 0.9

## Code & architecture
- For React/Next.js client state that must sync with browser-only storage (e.g., a localStorage-persisted theme), prefers hydration-safe patterns: a deterministic initial render shared by server and first client render, then synchronization with the persisted value after hydration/mount (mounted flag or useSyncExternalStore). Draws a sharp line between logic-level mismatches (toggle label/state — must be fixed with hydration-safe patterns so the toggle works without page reload) and attributes set by an external pre-paint script on `<html>` (e.g., `data-theme`): for that specific case, `suppressHydrationWarning` on the `<html>` tag is accepted as the correct, targeted fix (the pattern `next-themes` uses), not a hack. Rejects introducing a third-party theme/state library; no-flash behavior must be preserved. Confidence: 0.85
