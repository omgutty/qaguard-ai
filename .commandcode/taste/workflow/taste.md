# Taste

## Project structure
- Avoids creating empty/over-engineered folder structures ahead of need — explicitly said "don't create these folders manually yet; we'll create them when we actually need them" to prevent empty scaffolding. Creates folders/files only when actually needed. Confidence: 0.95

## Development process
- Prefers milestone-based incremental delivery: get a small working, verifiable slice done first (e.g., static UI), verify it, checkpoint, deploy, and only then layer in complexity (agents, AI, APIs). Confidence: 0.95
- Handles the git and deployment lifecycle himself: commits to GitHub and pushes to Vercel on his own, then reports production status back (e.g., "i have committed to github repo and pushed to vercel as well, requirement analyzer is working without any issue in vercel"). The assistant should not assume it owns committing/deploying, and should treat the user's production verification reports as the signal to proceed to the next phase. Confidence: 0.8
- Wants meaningful git checkpoints at verified milestones ("first meaningful commit"), not premature or trivial commits. Confidence: 0.85
- Maintains build/design specifications as markdown files inside the repo (e.g., `src/prompt/phase2prompt.md`, `src/prompt/uiprompt.md`, `src/prompt/RealRequirementAgent.md`) and references them in requests, expecting the agent to read and implement exactly to spec — including matching a referenced UI reference design. Confidence: 0.9
- Likes to keep the dev server (`npm run dev`) running throughout development and wants the assistant to leave it running; the user may also run their own instance in their own terminal, so check for existing listeners on the port before starting/restarting one. When the user starts their own instance, they explicitly direct the assistant to use it (e.g., "i have starteed dev server, with 3000 please continue") rather than spinning up its own on a different port. Confidence: 0.9
- Wants strict scope discipline: no unrequested technologies (explicitly no Langflow, n8n, MCP, RAG, database, Docker, Redis, Kafka, or Redux/state libraries), no unnecessary package installs, no future-stage logic (e.g., real LLM integration in Phase 1) before its step, and no advancing to the next feature/phase until asked ("For this step ONLY" / "Do not proceed to the next feature" / "Stop once Phase 1 is complete"). In bug-fix tasks this extends to explicit do-not-touch subsystem boundaries ("Fix ONLY the theme hydration issue", "DO NOT change the OpenRouter implementation / Requirement Agent / API routes / QAGuard workflow") — touch only the named files and nothing else. Prefers minimal placeholder stubs to keep TypeScript clean over speculative implementation. Confidence: 0.95
- When a reference UI/document is provided "for color reference," applies only the colors/theme to the existing UI and reverts any structural additions (new nav items, extra widgets) that go beyond the reference's stated purpose. Confidence: 0.85
- Prefers existing working UI/code to be left untouched unless the current task requires changes ("DO NOT redesign or remove the existing UI"). Confidence: 0.85
- Wants post-change verification: run the project's lint and TypeScript/build checks, ensure zero errors (explicitly "no unresolved warnings caused by your own code"), then start the dev server and verify runtime behavior (no hydration errors in the browser console, dark/light modes work, refresh preserves persisted state, no flash), and show the created files plus verification results. Confidence: 0.9
- Tooling environment note: this user's npm is configured with `omit=dev` (devDependencies skipped on plain `npm install`), which can silently break builds — installs in this project need `npm install --include=dev`. Confidence: 0.7
- Wants mock/"AI" layers built as deterministic functions that derive believable results from actual input (never hardcoded or random), architected with stable public function signatures so internals can be swapped for real LLM calls later without changing the API. Confidence: 0.9
- Wants strict TypeScript data contracts: zero `any`, union types for controlled vocabularies (statuses, types, priorities), modeled only for the current phase with no speculative fields, and reusable cross-cutting logic centralized in shared lib helpers rather than duplicated per screen. Confidence: 0.85
- Wants explicit governance/business-rule enforcement in logic, not just UI copy (e.g., unapproved test cases cannot reach automation) and no fake claims — README and UI must state clearly when functionality is mocked vs real ("Do not claim real AI functionality"). Confidence: 0.8
- Wants the README kept current with the actual product state, not stale phase placeholders — once AI is integrated, remove "current phase" / "future AI integration" sections and instead document in detail what v1 and v2 each actually accomplished. Confidence: 0.85
- Wants the final README to follow a standard complete deliverable structure: Project Title, Problem Statement, Solution, Tech Stack, How to Run, Demo (Vercel link), Screenshots. Confidence: 0.9
- Wants no internal development-phase markers in the shipped product UI (e.g., a "Phase 1" badge in the dashboard top-right) — user-facing surfaces should show the final product state, not the build history. Confidence: 0.8
- Treats leaked secrets as a critical incident: when a real API key is found committed to git (even in a tracked `.env.local.example`), expects immediate scrubbing of the working file, an explicit call to rotate the key (treat as compromised), and a flag that history purge (filter-repo) is the user's destructive decision — never rewritten unilaterally. Confidence: 0.9
- Wants critical fixes/decisions surfaced at the end of the work in an explicit issues/decisions section of the deliverable report (e.g., "no git commit created", deliberate deviations like moving mock agents server-side). Confidence: 0.7
